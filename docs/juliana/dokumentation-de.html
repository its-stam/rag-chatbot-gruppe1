1. Ausgangssituation des Unternehmens

1.1 Fallunternehmen BergTech Maschinenbau GmbH

Das Projekt ist als Auftragsarbeit für die fiktive BergTech Maschinenbau GmbH formuliert — ein mittelständisches Industrieunternehmen mit rund 450 Mitarbeitenden, das aus der Saile-Aufgabenstellung „Case 1 — HR Knowledge Assistant" abgeleitet ist. BergTech steht stellvertretend für einen typischen deutschen Industriebetrieb: eine etablierte, prozessgetriebene Organisation mit ausdifferenzierter Personalpolitik, regelmäßigem Onboarding und gewachsener Compliance-Landschaft.

1.2 Geschäftliches Problem

Die zentrale Personalabteilung der BergTech ist mit einer hohen Frequenz an repetitiven Mitarbeiteranfragen konfrontiert. Drei Themencluster dominieren das Anfragevolumen:

  • Onboarding — Welche Unterlagen sind vor dem ersten Arbeitstag einzureichen? Welche Pflichttrainings stehen an?
  • Urlaub und Abwesenheit — Wie viele Tage im Voraus muss Urlaub beantragt werden? Wie ist die Krankmeldung geregelt?
  • Compliance & Schulungen — Welche Pflichtschulungen sind im Onboarding vorgesehen? Welche Fristen gelten?

Diese Fragen sind in den fünf zentralen HR-Dokumenten (Onboarding-Guide, Vacation Policy, Compliance Policy, HR-FAQ, Offboarding Checklist) bereits vollständig beantwortet — die Mitarbeitenden finden sie dort jedoch nicht schnell genug, weil die Dokumente verteilt im Intranet liegen und keine kontextbezogene Suche bieten. Die HR-Abteilung beantwortet dieselbe Frage daher mehrfach pro Woche manuell.

1.4 Lösungsansatz: Retrieval-Augmented Generation

Wir realisieren einen Chatbot auf Basis des Architekturmusters Retrieval-Augmented Generation (RAG), das von Lewis et al. (2020) als Verfahren eingeführt wurde, um parametrisches Sprachmodell-Wissen mit nicht-parametrischem externem Wissen zu koppeln[1]. Konkret bedeutet das: Anstatt ein Large Language Model (LLM) auf die HR-Dokumente nachzutrainieren (Fine-Tuning) — was rechenintensiv und schwer zu aktualisieren wäre — werden die Dokumente vorab in eine Vektordatenbank geladen und bei jeder Nutzerfrage die relevantesten Textfragmente an das Sprachmodell als Kontext mitgegeben. Das Modell antwortet ausschließlich auf Basis dieser Fragmente. Aktuelle Übersichten zeigen, dass RAG-Ansätze die Halluzinationsrate von LLMs deutlich reduzieren und gleichzeitig die Aktualisierbarkeit der Wissensbasis garantieren[8][7].

2.2 Hochlevel-Datenfluss

Das System besteht aus zwei voneinander entkoppelten Pfaden auf einer gemeinsamen n8n-Canvas:

  1. Ingestion-Pfad (einmalig oder bei Dokumentänderungen ausgeführt): Lädt die HR-Markdown-Dateien, zerlegt sie in Textabschnitte (Chunks), erzeugt Vektorrepräsentationen und schreibt sie in die Tabelle documents.
  2. Query-Pfad (pro Nutzeranfrage ausgeführt): Empfängt die Frage über die n8n-Chat-Sidebar, vektorisiert sie mit demselben Embedding-Modell, sucht über pgvector die acht ähnlichsten Chunks und übergibt sie dem LLM zur Antwortformulierung.

Die beiden Pfade sind bewusst nicht miteinander verdrahtet — die einzige Kopplung ist die geteilte Datenbank. Dadurch ist die Ingestion ein separater Verwaltungsvorgang, der die Antwortzeit der Live-Abfragen nicht beeinflusst.

2.3 Definitionen zentraler Begriffe

  • Embedding — Eine dichte Vektorrepräsentation von Text in einem hochdimensionalen Raum, in dem semantisch ähnliche Texte räumlich nah beieinanderliegen. Wir nutzen 1536-dimensionale Embeddings nach Reimers & Gurevych (2019)[3].
  • Chunk — Ein semantisch zusammenhängender Textausschnitt, der durch einen Text-Splitter aus einem Quelldokument erzeugt wird. Wir verwenden Chunks von 500 Zeichen Länge mit 50 Zeichen Überlappung.
  • Cosine Similarity — Ein Maß für die Ähnlichkeit zweier Vektoren, das den Kosinus des eingeschlossenen Winkels berechnet. Wertebereich: −1 (entgegengesetzt) bis +1 (identische Richtung). Bei normierten Embedding-Vektoren ist sie das De-facto-Standardmaß[2].
  • HNSW (Hierarchical Navigable Small World) — Ein graphbasierter Index für approximative Nächste-Nachbar-Suche mit logarithmischer Komplexität, vorgestellt von Malkov & Yashunin (2020)[4]. Wir setzen ihn in pgvector über using hnsw (embedding vector_cosine_ops) ein.
  • Top-k — Die Anzahl der ähnlichsten Vektoren, die das Retrieval zurückgibt. Wir nutzen k = 8.

3. Detaillierter Workflow

3.1 Ingestion-Pfad

Der Ingestion-Pfad wird über einen Manual Trigger manuell gestartet — bewusst nicht automatisiert, weil sich die HR-Policies nur quartalsweise ändern und ein versehentliches Re-Ingest die Datenbank überfluten würde. Die fünf HR-Markdown-Dokumente liegen unter company-docs/anastasiia/.

#n8n-NodeFunktionKonfiguration
1READ MD-File (Manual Trigger)Auslöser—
2Read/Write Files from DiskLesen der fünf .md-DateienfileSelector: ~/.n8n-files/company-docs/anastasiia/**/*.md
3Recursive Character Text SplitterZerlegung in ChunkschunkSize: 500, chunkOverlap: 50
4Default Data LoaderKombiniert Splitter und Loader, fügt Metadaten andataType: binary, loader: textLoader, textSplittingMode: custom
5Embeddings OpenAIVektorisierungModell text-embedding-3-small (1536 dim)
6Supabase Vector Store (insert)PersistenztableName: documents, queryName: match_documents

Designentscheidung: 500 Zeichen, 50 Zeichen Overlap

HR-Richtlinien bestehen aus kurzen, dichten Abschnitten — eine Urlaubsregel oder ein FAQ-Eintrag ist typischerweise 200–600 Zeichen lang. Ein Chunk von 500 Zeichen umfasst damit in der Regel eine abgeschlossene Regel und vermeidet, dass zwei thematisch unterschiedliche Abschnitte vermischt werden. Der Overlap von 50 Zeichen kompensiert das Risiko, dass eine Regel genau an der Chunk-Grenze abgeschnitten wird. Dieses Verhältnis von ca. 10% Overlap entspricht gängiger Praxis in der RAG-Literatur[8].

Achtung — Zeichen, nicht Tokens. Der RecursiveCharacterTextSplitter in n8n arbeitet zeichenbasiert. 500 Zeichen entsprechen für deutsche HR-Texte etwa 125–200 Tokens (Wortteile, mit denen ein LLM intern rechnet). Diese Klarstellung ist wichtig, weil viele RAG-Tutorials die Chunk-Größe in Tokens angeben.

Designentscheidung: Embedding-Modell explizit setzen

Beide Embedding-Nodes — Ingestion und Query — sind hartkodiert auf text-embedding-3-small konfiguriert. Würde man stattdessen das Modell als options: {} weglassen, fiele n8n auf den OpenAI-Default ada-002 zurück. Eine spätere Default-Änderung des Providers würde unbemerkt zu einer Inkonsistenz zwischen Schreib- und Lesepfad führen — die Vektoren würden nicht mehr in dieselbe geometrische Lage projiziert, das Retrieval würde leer liefern. Dies ist ein klassischer Implementierungsfehler, der nur durch explizite Konfiguration vermeidbar ist.

3.2 Query-Pfad

#n8n-NodeFunktionKonfiguration
1When chat message receivedChat-Trigger über n8n-SidebarLangChain-Chat-Trigger, public: true
2AI AgentOrchestrierung: entscheidet über Tool-Aufruf, ruft LLM, formatiert AntwortopenAiFunctionsAgent, gehärteter System-Prompt
3OpenAI Chat Model (Sub-Node)AntwortformulierungModell gpt-5-mini
4Embeddings OpenAI (Sub-Node)Vektorisierung der Nutzerfragetext-embedding-3-small
5Supabase Vector Store (Tool)Retrieval der Top-8 Chunksmode: retrieve-as-tool, topK: 8

Designentscheidung: topK = 8

Wir haben den ursprünglichen Wert von k = 5 nach einem End-to-End-Test am 30.05.2026 auf k = 8 erhöht. Die Beobachtung: einzelne Themen (z.B. Arbeitszeitregelung) sind nur in einem oder zwei Chunks belegt; bei k = 5 konkurrieren sie mit häufigeren Themen und werden manchmal verdrängt. Eine Erhöhung auf k = 8 reduziert das Risiko, einen relevanten Chunk zu „verlieren", auf Kosten eines geringfügig größeren Kontextfensters für das LLM. Das ist ein klassischer Recall-vs-Präzisions-Trade-off und konsistent mit den empirischen Erkenntnissen von Karpukhin et al. zur Wirkung von k[2].

Designentscheidung: Cosine Similarity statt euklidische Distanz

OpenAI-Embeddings sind L2-normiert; die geometrische Information liegt in der Richtung, nicht in der Magnitude. Cosine Similarity vergleicht ausschließlich die Richtung und ist damit der theoretisch passende Vergleich. Sie ist außerdem der Standard in pgvector (vector_cosine_ops).

Designentscheidung: Gehärteter System-Prompt

Der zentrale Sicherheitsmechanismus gegen Halluzination ist nicht das LLM, sondern der System-Prompt des AI Agents. Die wesentlichen Regeln:

Du bist der HR-Assistant der BergTech Maschinenbau GmbH.

ARBEITSWEISE (zwingend):
  - Bei JEDER inhaltlichen Frage rufst du ZUERST das Tool
    "Supabase Vector Store" auf. Ohne Ausnahme.
  - Du stellst KEINE Rückfragen bevor du gesucht hast.
  - Du nutzt AUSSCHLIESSLICH den Inhalt der gefundenen Dokumente.

ANTWORT:
  - Antworte knapp und konkret mit den Fakten aus den Dokumenten.
  - Nenne die Quelle als [Dokumentname].
  - Wenn die Suche NICHTS Passendes liefert:
    "Diese Information liegt mir in den HR-Dokumenten nicht vor.
     Bitte wende dich an hr@bergtech.de."

VERBOTEN:
  - Allgemeine Firmenregel-Listen oder Vorlagen erstellen.
  - Auf gesetzliche Mindeststandards ausweichen.
  - Antworten ohne vorherigen Tool-Aufruf.

Der Prompt instrumentalisiert eine zentrale Erkenntnis der Prompting-Forschung: Direkte, restriktive Anweisungen sind effektiver als höfliche Hinweise[5][19]. In Vorversionen war der Prompt weicher formuliert („antworte auf Basis der Dokumente"), woraufhin der Agent gelegentlich auf allgemeines Weltwissen zurückfiel.

Designentscheidung: Temperature 0 — und warum nicht 0.3

Die Temperature ist ein Sampling-Parameter, der die Zufälligkeit der Token-Auswahl beim Decoding steuert. Bei T = 0 wird greedy decoded — das Modell wählt bei jedem Schritt deterministisch das Token mit der höchsten Wahrscheinlichkeit. Höhere Werte (typisch T = 0.7 bis 1.0) flachen die Verteilung ab und erzeugen kreativere, variantenreichere Ausgaben[6].

Für faktentreue, dokumenten­gestützte Q&A-Anwendungen — wie unseren HR-Chatbot — empfiehlt sowohl die einschlägige RAG-Literatur als auch die offizielle Anbieterdokumentation einen Temperatur-Bereich von 0 bis 0.3: niedrige Werte minimieren Halluzinationen und sichern Reproduzierbarkeit der Antworten[8][7][20]. Höhere Werte (≥ 0.7) sind für kreative oder explorative Aufgaben gedacht (Story-Generierung, Brainstorming) und sind für HR-Auskünfte mit rechtlicher Relevanz kontraindiziert: Dieselbe Frage darf nicht heute „14 Tage Vorlauf" und morgen „eine Woche reicht auch" beantworten.

Innerhalb dieses Korridors haben wir uns für den unteren Extremwert T = 0 entschieden. Die initiale Konfiguration unter Anthropic Claude 3 Haiku lief auf T = 0.3 — ein für Kundensupport-Chatbots üblicher Industriewert, der den Antworten eine geringe stilistische Variation erlaubt, ohne die Faktenbasis zu gefährden. Nach dem Wechsel auf den OpenAI Functions Agent und der Bug-Serie vom 29.–30.05.2026, bei der das Modell trotz Tool-Verfügbarkeit auf Allgemeinwissen auswich (siehe Kap. 7.3), haben wir die Determinismus-Anforderung weiter verschärft: Determinismus wird jetzt zusätzlich durch den restriktiven System-Prompt erzwungen („antworte knapp und konkret mit den Fakten"). Der API-Parameter selbst ist im aktuellen n8n-Export nicht explizit gesetzt; in einer Produktivversion würden wir temperature: 0 redundant auch als Node-Parameter hartkodieren, damit Provider-Default-Änderungen die deterministische Eigenschaft nicht unterlaufen können — eine direkte Konsequenz aus unserer Embedding-Default-Erfahrung (Kap. 7.3, Bug #5).

3.3 Datenbankschema

create extension if not exists vector;

create table documents (
  id        bigserial primary key,
  content   text,           -- Chunk-Text
  metadata  jsonb,           -- Dateiname + Quelle
  embedding vector(1536)     -- text-embedding-3-small
);

create index on documents
  using hnsw (embedding vector_cosine_ops);

alter table documents enable row level security;
create policy "service_role full access"
  on documents for all to service_role
  using (true) with check (true);

Die Row-Level-Security-Policy stellt sicher, dass nur n8n (mit dem service_role-Key) Zugriff hat. Der öffentliche anon-Key wäre andernfalls in der Lage, die gesamte Vektor-Tabelle auszulesen — ein häufig übersehenes Sicherheitsrisiko bei Supabase-Projekten[17].

4.1 Fallback-Verhalten

Bei Fragen außerhalb des Wissensbestands antwortet der Bot mit dem deterministischen Satz: „Diese Information liegt mir in den HR-Dokumenten nicht vor. Bitte wende dich an hr@bergtech.de." Dieser Fallback ist die wichtigste Schutzschicht gegen Halluzination und gleichzeitig die Umsetzung der Transparenzpflicht aus Art. 50 EU-AI-Act (Kapitel 6).

4.2 Erkannte Grenze: dünn belegte Themen

Im Test zeigte sich, dass die Frage „Wie sind die Arbeitszeiten?" inkonsistent beantwortet wird — die Information steht nur als nebenbei erwähnter Satz im Onboarding-Guide, hat dadurch ein schwaches Embedding-Signal und wird selbst mit k = 8 nicht zuverlässig retrievt. Mitigation: Ergänzung einer expliziten FAQ-Q&A zum Thema Arbeitszeit (siehe docs/vorschlag-arbeitszeit-faq.md). Dies illustriert eine generelle Eigenschaft semantischer Retrieval-Systeme: was im Korpus selten erwähnt wird, ist auch im Vektorraum schwach repräsentiert.

5.2 Verbleibende Restrisiken

Wir benennen drei Restrisiken explizit, weil sie für eine Produktivumgebung adressiert werden müssten, im Rahmen des Prototyps aber bewusst akzeptiert sind:

  • Single-Provider-Risiko. Der Wechsel auf All-OpenAI reduziert Integrationsfehler, schafft aber ein einzelnes Ausfallszenario. In einem Produktivsystem würden wir ein Failover auf einen zweiten Provider (z.B. Anthropic oder Mistral) ergänzen.
  • Kein End-to-End-Audit-Trail. Aktuell werden Anfragen und Antworten nicht persistent protokolliert. Für eine HR-Anwendung mit rechtlicher Relevanz wäre ein revisionssicheres Logging notwendig.
  • Keine kontinuierliche Qualitätsmessung. Wir haben keinen automatisierten Evaluator (z.B. RAGAS oder Truelens) integriert. Eine Produktivversion sollte die Antwortqualität laufend mit synthetischen und realen Fragen messen.

6. EU-AI-Act-Konformitätsanalyse

Die Verordnung (EU) 2024/1689 (im Folgenden: EU-AI-Act)[9] ist seit 01. August 2024 in Kraft. Sie definiert risikobasierte Pflichten für die Entwicklung und den Einsatz von KI-Systemen in der Europäischen Union. Wir analysieren das Projekt entlang vier Dimensionen: Akteursrollen, Risikoklasse, anwendbare Pflichten und deren konkrete Umsetzung.

6.2 Risikoklassifizierung

Der EU-AI-Act unterscheidet vier Risikostufen: unacceptable risk (verboten, Art. 5), high risk (Art. 6 ff.), limited risk (Transparenzpflichten, Art. 50) und minimal risk. Unser System fällt in die Klasse Limited Risk, weil:

  • Der Chatbot interagiert direkt mit natürlichen Personen → Art. 50 Abs. 1 ist anwendbar.
  • Er trifft keine rechtswirksamen Entscheidungen (z.B. über Einstellung, Beförderung, Entlassung). Hochrisiko-Tatbestände nach Anhang III Nr. 4 (Beschäftigung, Personalmanagement) sind damit nicht erfüllt.
  • Antworten sind nicht-bindende Informationsauskünfte; finale Entscheidungen liegen bei HR.

Diese Einordnung ist konsistent mit der Auslegung in Veale & Zuiderveen Borgesius (2021), die den Anwendungsbereich von Art. 50 für rein informationsgebende Chatbots ausführlich diskutieren[10], sowie mit der Übersichtsdarstellung des Ada Lovelace Institute[12].

6.4 Empfehlungen für den Produktivbetrieb (BergTech-Rollout)

Auch wenn das System in der Limited-Risk-Klasse einzuordnen ist, empfehlen wir BergTech als Deployer drei zusätzliche Maßnahmen analog zu Hacker et al. (2023), die für generative Systeme strengere Standards vorschlagen[11]:

  1. Sichtbarer KI-Hinweis im Chat-Header (Banner: „Sie chatten mit einem KI-System. Antworten sind unverbindlich und ersetzen keine HR-Beratung.")
  2. Quartalsweise Policy-Audits: stimmen Dokumente in der Wissensbasis noch mit den aktuellen Policies überein?
  3. Beschwerde-Pfad: Möglichkeit für Nutzer, eine Antwort als falsch zu markieren, mit Eskalation an HR.

7. Implementierungsreflexion

7.1 Drei zentrale Designentscheidungen

EntscheidungBegründungBewertung im Rückblick
n8n als Orchestrator (statt LangChain pur) Visuelle Modellierung, einfacher Export, native Sub-Node-Architektur, Saile-Vorgabe „einfach halten" Tragfähig. Hat die Lernkurve am Anfang verlängert, aber die Reproduzierbarkeit und Demo-Tauglichkeit deutlich erhöht.
Supabase mit pgvector (statt Pinecone/Weaviate) Kostenfreier Tier, vertrautes PostgreSQL, EU-Region, RLS Stark. match_documents-Setup war initial knifflig (Ambiguity-Bug, siehe 7.3), funktioniert aber stabil.
Linearer RAG-Flow (statt Agentic Loop mit Plan-Execute-Reflect) HR-FAQ ist single-hop, Saile-Vorgabe wenig Nodes, Reflection-Loops können sich verlaufen Korrekt. Für unseren Anwendungsfall bringt ein Agentic Loop keinen messbaren Mehrwert und erhöht das Failure-Risiko in der Live-Demo.

7.2 Was gut gelaufen ist

  • Systematisches Debugging über sieben Live-Bugs hinweg. Am 29.–30.05. trat eine Kette von Blockern auf (Dateizugriff, OpenAI-Kontingent, Agent-Typ, Modell-Retirement, fehlende RPC, SQL-Ambiguität, Data-Loader-Bug). Jeder Fehler wurde isoliert und an der Wurzel gefixt, statt symptomatisch zu kompensieren.
  • Pragmatische Architekturanpassung unter Druck. Als das Anthropic-Chatmodell während des End-to-End-Tests am 30.05. mit einem 404-Fehler abgewiesen wurde (Modell-Retirement), erfolgte ein klarer Cut auf All-OpenAI (gpt-5-mini). Statt im Modell-Problem zu verharren, wurde die Architektur an die Verfügbarkeit angepasst.
  • Trennung von Stabilität und Eleganz vor der Demo. n8n 2.22.5 wurde am 30.05. installiert, aber bewusst nicht durch Prozess-Neustart aktiviert — der laufende Agent (basierend auf 2.17.7 mit OpenAI-Functions-Agent) blieb in seiner getesteten Konfiguration.

7.4 Fünf zentrale Learnings

  1. Defaults nie blind vertrauen. Provider können Defaults jederzeit ändern. Modellnamen explizit in der Konfiguration setzen.
  2. Datenmenge ≠ Datenqualität. SELECT count(*) FROM documents beweist nichts. Nach Ingestion stichprobenartig den content auslesen.
  3. Tool-Nutzung muss im Prompt erzwungen werden. LLMs wählen den Weg des geringsten Widerstands; ohne harte Anweisung umgehen sie das Tool.
  4. Single-Provider reduziert die Integrationsoberfläche. Die ursprünglich eleganter wirkende Multi-Provider-Architektur (Anthropic+OpenAI) wurde zur Fehlerquelle (Retirement). Ein Provider ist robuster für einen Demo-Termin.
  5. n8n-Workflows in der UI bauen, nicht im JSON. Der JSON-Export ist Output, kein Input. Manuelles JSON-Editieren erzeugt subtile Inkonsistenzen.

7.5 Ausblick: Weiterentwicklungspfade

Das vorgestellte System ist ein lauffähiger Prototyp auf MVP-Niveau. Für den produktiven Einsatz bei BergTech und vergleichbaren mittelständischen Unternehmen sehen wir sechs konkrete Weiterentwicklungspfade, geordnet nach erwartetem Nutzen-Aufwand-Verhältnis.

(1) Retrieval-Qualität verbessern

  • Hybrid Retrieval — Kombination unserer semantischen Vektorsuche mit einer lexikalischen BM25-Suche. Adressiert die in Kap. 4.2 dokumentierte Schwäche bei dünn belegten Themen (Arbeitszeit-Frage), in der Literatur als komplementäre Stärke von Dense und Sparse Retrieval etabliert[2][8].
  • Cross-Encoder-Re-Ranking — die Top-30-Kandidaten aus Cosine-Suche mit einem zweiten, präziseren Modell (z.B. bge-reranker) neu sortieren. Erhöht die Präzision deutlich bei nur marginal höheren Kosten.
  • Adaptive top-k — bei einfachen Faktenfragen k = 3, bei komplexen Mehrteil-Fragen k = 12. Reduziert Kontextfenster-Rauschen und LLM-Kosten.

(2) Generation-Qualität & Konsistenz

  • Temperature explizit als API-Parameter setzen (siehe Kap. 3.2). Aktuell wird Determinismus nur über den Prompt erzwungen — eine doppelte Absicherung über temperature: 0 auf Node-Ebene wäre robuster.
  • Streaming Responses — Antworten Token für Token ausgeben statt am Stück. Reduziert die wahrgenommene Latenz erheblich; in n8n erfordert dies einen Wechsel des AI-Agent-Nodes (Tools Agent ab n8n 2.22.5).
  • Conversation Memory — Folgefragen wie „und was ist mit Kurzurlauben?" auflösen, ohne dass Nutzer die Frage neu formulieren müssen. In n8n via LangChain-Memory-Sub-Node implementierbar; entscheidend ist eine Session-ID, die an die Chat-Sidebar bindet.

(3) Daten & Operations

  • Automatisierter Re-Ingest — Trigger über Git-Hook oder Sharepoint-Webhook: sobald ein HR-Dokument aktualisiert wird, läuft die Ingestion-Pipeline. Eliminiert das größte operative Risiko (veraltete Wissensbasis).
  • Versionsmetadaten in der metadata-Spalte (z.B. {"version": "2026-Q2", "valid_from": "2026-04-01"}). Erlaubt Stichtags-Antworten („Was war die Regelung am 1. Mai?") und sauberes Rollback.
  • Upsert statt Truncate-and-Insert — bei Re-Ingest nur die geänderten Chunks ersetzen, nicht die gesamte Tabelle leeren. Vermeidet kurzzeitige Antwort-Ausfälle und schont das Embedding-API-Kontingent.

(4) Evaluierung & Qualitätsmessung

  • RAGAS-Integration — automatisierte Bewertung jeder Antwort mit den Metriken Faithfulness, Answer Relevancy und Context Precision (siehe Definitionen in Ji et al. 2023[7]).
  • Goldfragen-Suite — 30–50 manuell kuratierte Fragen mit erwarteten Antworten + Quellen, die in CI nach jedem Re-Ingest geprüft werden. Verhindert Regressionen.
  • Drift-Detection — wöchentliche Vergleichsläufe; signifikante Veränderungen in Antwortverteilung melden.

(5) Skalierung & Multi-Modal

  • PDF-Loader mit Tabellen- und Bild-Extraktion (z.B. unstructured.io). Aktuell reine Markdown-Verarbeitung; produktive HR-Dokumente enthalten oft Tabellen und Diagramme, deren Inhalt verlorengeht.
  • Mehrsprachigkeit — viele Industriebetriebe haben internationale Belegschaft. Zwei Optionen: separate Vektor-Tabelle pro Sprache oder ein multilinguales Embedding-Modell (z.B. multilingual-e5-large).
  • Caching-Schicht — exakt oder semantisch identische Wiederholfragen aus einem Cache beantworten. Spart deutlich LLM-Kosten bei skalierender Nutzung.

(6) Compliance, Governance & Sicherheit

  • Revisionssichere Audit-Logs — jede Frage, jede retrievte Chunk-ID und jede Antwort persistent loggen. Pflicht für rechtlich relevante HR-Auskünfte.
  • Feedback-Pfad — „War diese Antwort hilfreich?"-Button; negative Bewertungen automatisch an HR eskalieren. Adressiert Art. 50 Abs. 5 EU-AI-Act.
  • Granulare RLS — Zugriffsrechte je HR-Dokument: nicht jeder Mitarbeiter darf das Compliance-Handbuch sehen. Lässt sich über metadata-Filter in der match_documents-RPC abbilden.
  • Prompt-Injection-Filter — Eingaben gegen bekannte Angriffsmuster prüfen (z.B. „Ignore previous instructions"). Aktuell nur durch System-Prompt-Robustheit mitigiert.

Priorisierung

Würden wir die Arbeit fortsetzen, wäre die Reihenfolge: (a) Automatisierter Re-Ingest und RAGAS-Goldfragen als Operations-Grundlage, (b) Hybrid Retrieval und explizite Temperature als Qualitäts-Quick-Wins, (c) Audit-Logs und Feedback-Pfad als Compliance-Pflicht vor BergTech-Rollout, (d) Conversation Memory und Multi-Modal als nutzerseitige Komfortverbesserungen.

8.5 Glossar

Approximate Nearest Neighbor (ANN)
Verfahren zur näherungsweisen Suche der nächsten Nachbarn in hochdimensionalen Räumen mit logarithmischer statt linearer Laufzeit. Wir nutzen den HNSW-Algorithmus.
Chunk
Ein semantisch zusammenhängender Textabschnitt fester (oder geregelter) Maximallänge, der durch einen Splitter aus einem Quelldokument erzeugt wird.
Cosine Similarity
Ähnlichkeitsmaß, das den Kosinus des Winkels zwischen zwei Vektoren berechnet. Standardmaß für normierte Embedding-Vektoren.
Embedding
Dichte numerische Vektorrepräsentation von Text in einem hochdimensionalen Raum, in dem semantische Ähnlichkeit als räumliche Nähe abgebildet ist.
GPAI (General-Purpose AI)
Begriff aus dem EU-AI-Act für universell einsetzbare KI-Modelle (z.B. GPT-Familie). Unterliegen besonderen Pflichten nach Art. 51 ff.
Halluzination
Generierung von Inhalt, der plausibel klingt, aber faktisch falsch oder nicht im Kontext belegt ist. Zentrales Risiko bei LLMs.
HNSW (Hierarchical Navigable Small World)
Graphbasierter Index für approximative Nächste-Nachbar-Suche mit hervorragender Performance bei Embeddings.
Limited Risk
Risikoklasse des EU-AI-Acts für KI-Systeme, die direkt mit natürlichen Personen interagieren, ohne rechtswirksame Entscheidungen zu treffen. Hauptpflicht: Transparenz (Art. 50).
pgvector
PostgreSQL-Erweiterung, die einen vector-Datentyp und Ähnlichkeitsoperatoren für Embedding-basierte Suche bereitstellt.
RAG (Retrieval-Augmented Generation)
Architekturmuster, das ein LLM zur Generierung mit einem externen Retrieval-System kombiniert, um faktentreue Antworten ohne Fine-Tuning zu ermöglichen.
Row-Level-Security (RLS)
PostgreSQL-Sicherheitsmechanismus, der Zugriffe auf Zeilenebene über Policies steuert. Pflicht für Supabase-Tabellen im public-Schema.
System-Prompt
Anweisungstext, der dem LLM vor jeder Nutzerinteraktion mitgegeben wird und Rolle, Verhalten und Beschränkungen festlegt.
Temperature
Sampling-Parameter, der die Schärfe der Wahrscheinlichkeits­verteilung über das nächste Token beim Decoding steuert. T = 0 erzwingt greedy decoding (deterministisch); T < 1 verschärft die Verteilung; T > 1 flacht sie ab. Für faktentreue RAG-Systeme empfehlen sowohl Lehrbuchliteratur als auch Anbieter-Dokumentationen T ∈ [0, 0.3][6][20].
Token
Kleinste textuelle Einheit, mit der ein LLM rechnet (typischerweise Wortteile). Ein deutscher Satz hat etwa 1,5–2× so viele Tokens wie Wörter.
Vektordatenbank
Datenbank, die für die Speicherung und Ähnlichkeitssuche von Embedding-Vektoren optimiert ist.

A.2 Supabase-Schema (vollständig)

create extension if not exists vector;

create table documents (
  id        bigserial primary key,
  content   text,
  metadata  jsonb,
  embedding vector(1536)
);

create or replace function match_documents (
  query_embedding vector(1536),
  match_count int default null,
  filter jsonb default '{}'
) returns table (
  id bigint,
  content text,
  metadata jsonb,
  similarity float
)
language sql
as $$
  select d.id, d.content, d.metadata,
         1 - (d.embedding <=> query_embedding) as similarity
  from documents d
  where d.metadata @> filter
  order by d.embedding <=> query_embedding
  limit match_count;
$$;

create index on documents
  using hnsw (embedding vector_cosine_ops);

alter table documents enable row level security;

create policy "service_role full access"
  on documents for all to service_role
  using (true) with check (true);
